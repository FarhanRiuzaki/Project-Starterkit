# API contract

What the API answers: `apps/api`, Bun + Elysia + Drizzle on PostgreSQL, one module per area under
`apps/api/src/modules/`. The browser calls `/api/x` on the Next server; Next forwards it to the API at `/v1/x` (same
path below `/v1`, same method, query and body), so every `/api/...` path in this document is also the API's `/v1/...`
path. The source of truth is the zod schemas in `packages/shared/src/contracts/*`, which the web and the API both
import; `schemas/` holds one JSON Schema (draft 2020-12) per schema, generated by `bun run api:schemas`
(`apps/web/scripts/emit-api-schemas.ts`, zod's `z.toJSONSchema`). Do not edit `schemas/` by hand:
`apps/web/src/test/api-contract.test.ts` fails when the files differ from the zod source, and
`apps/api/test/architecture/conformance.test.ts` fails when the endpoint table below misses a route of the API or lists
one it doesn't serve.

Request schemas (`…Body`, `…Query`) describe what the client sends: a field with a `default` may be left out. Every
other schema describes the answer exactly (`additionalProperties: false`).

## Rules for every endpoint

- The browser calls only same-origin `/api/*` on the Next server. The backend is reached from Next server code
  through `API_BASE_URL` (server env); its address never reaches the browser.
- Answers are JSON with `Cache-Control: no-store`, except the CSV export and the OAuth redirects and landing page.
- Errors: `{ "error": { "code": string, "message": string } }` ([ApiErrorBody](schemas/ApiErrorBody.json)). The
  message is UI copy (English, says what happened and what to do); unknown failures are 500 `internal` with a fixed
  message, never the thrown text.
- Error codes and statuses are fixed: `unauthenticated` 401, `forbidden` 403, `csrf` 403, `not_found` 404,
  `bad_request` 400, `duplicate` 409, `rate_limited` 429, `invalid_credentials` 401, `account_inactive` 403,
  `invalid_code` 400, `superadmin_locked` 409, `last_superadmin` 409, `self_action` 409, `role_in_use` 409,
  `ldap_password` 409, `already_enabled` 409, `only_sign_in_method` 409, `internal` 500. One code is sent with
  another status on purpose: `invalid_credentials` is 400 when a signed-in user's current password is wrong
  (`PATCH /api/me`, `/api/me/password`, `/api/me/reauth`, `DELETE /api/me/2fa`), so the browser doesn't take it for
  an ended session.
- Check order in every guarded handler: parse the body or query (400) → session, CSRF, permission (401/403) →
  existence (404) → rules (403/409) → change → activity entry. A query is checked before the session (the GET rows
  below); a body's 400 comes right after the guard. `apps/api/test/architecture/conformance.test.ts` fails when a handler
  answers 404 before its body check.
- 429 answers send `Retry-After` in seconds.

### Sessions, CSRF, same origin

- The session is the `sk_session` cookie (sealed, `httpOnly`, `SameSite=Strict`, `Secure` when `COOKIE_SECURE=true`).
  It holds only the session id, the CSRF token and the pending-2FA marker; permissions are computed per request from
  the user's current roles, so a role change or a deactivation applies on the next request.
- Guarded endpoints (every row below with a permission or "signed in") check in this order: no live session → 401
  `unauthenticated`; a POST/PATCH/PUT/DELETE without the session's token in `x-csrf-token` (constant-time compare)
  → 403 `csrf`; missing permission → 403 `forbidden`, before any data is read. The signed-in layout hands the token to
  the browser.
- `/api/auth/*` POSTs carry no CSRF token (there is no session yet) but must be same-origin: `Sec-Fetch-Site:
  same-origin` (or `none`), or an `Origin` equal to the server's origin; otherwise 403 `forbidden`. Sign out with a
  full session needs `x-csrf-token` too.
- A sign-in that passed the password step of a 2FA account holds only the pending marker (10 minutes): every guarded
  endpoint answers it 401; it can only finish (`/api/auth/2fa`) or cancel (`/api/auth/logout`).
- A session ends `SESSION_TTL_HOURS` (default 12) after sign-in (`expiresAt`, absolute) or after
  `SESSION_IDLE_MINUTES` (default 120) without a request, whichever comes first. The next request with it answers
  401 and the record is deleted; lists and counts of sessions (`/api/me/sessions`, `/api/users/{id}/sessions`, the
  dashboard) drop ended ones first. Any request (API, page load, server prefetch) marks the session seen, but
  `lastSeenAt` is written at most once a minute, so it is accurate to a minute and idle time to a minute too.
- Changing a credential or the sign-in identity needs the current one again (re-authentication): the password change,
  turning 2FA off, and a new email on `PATCH /api/me` (`currentPassword`; the directory password for LDAP users).
  Wrong answers share the backoff below. An account that signs in only through Google or Apple keeps the provider's
  email (409 `self_action`), can't turn 2FA on (the provider checks it, so a code would never be asked; 400), and turns
  2FA off with a recovery code instead of a password.
- Connecting Google or Apple adds a way to sign in, so it needs a session that proved the user within the last 10
  minutes (`MeDto.reauthFresh`): a sign-in counts, and so does `POST /api/me/reauth` (the password, the directory
  password for LDAP users, or a recovery code for an account without a password). Otherwise the link start is 403
  `forbidden` and the browser lands on `/me/security?oauth=reauth`. An account with neither a password nor 2FA has no
  second proof: it signs in again (400 `bad_request` from `/api/me/reauth`).
- A password change ends the user's other sessions and spends their open reset and invitation links; an admin reset
  and a reset by link end all of their sessions.
- Sign-in steps (`login`, `2fa`) are limited per client IP (10 per minute), fleet-wide (300 per minute) and per
  username (5 per minute), with a soft backoff per username after 3 failures (1 s, 2 s, 4 s … up to 60 s, cleared
  after 15 quiet minutes or a success). A signed-in user's wrong current password or recovery code (`PATCH /api/me`,
  `/api/me/password`, `/api/me/reauth`, `DELETE /api/me/2fa`) backs off after 5 failures (one budget per user).
- `POST /api/auth/forgot` is limited per client IP (10 per minute) and per email (3 per 15 minutes). A throttled
  request still answers 200 `{ ok: true }` and sends nothing, so the limit reveals nothing about which emails exist.
- Every limiter and backoff is a PostgreSQL row (`rate_limits`, `login_backoff`, UNLOGGED tables) updated by one atomic
  upsert per attempt, so the limits hold across API processes; the janitor deletes rows that no longer count.

### Sign-in log

- Events: `login_success` (a sign-in without a second factor, OAuth included), `password_ok` (the password step of a
  2FA account passed; the code is still due), `2fa_success`, `2fa_failed`, `login_failed`, `logout`, and
  `password_reset` (a new password set through a reset or invitation link). A completed sign-in is `login_success` or
  `2fa_success`; the dashboard counts only those.
- `login` is the account's email whenever the attempt matched an account (typed as username or email), otherwise the
  text that was typed. `userId` is null for an unknown login. A Google/Apple attempt logs `method` = the provider;
  for an identity that isn't connected to a user, `login` is the provider's email (else its subject).

### Lists (paging)

- Query: `page` 1–1000 (default 1; deeper is 400, narrow the filters instead), `pageSize` 15, 25, 50 or 100 (default
  15), `q` up to 200 characters (lists that search), `sort` = `key` or `-key` from the endpoint's own list (the enum in
  its `…Query` schema), plus the endpoint's filters. A value outside these is 400 `bad_request`, checked before the
  session. Query values arrive as strings: `page` and `pageSize` are parsed as numbers (`?page=2`), so the JSON
  Schemas give their input type as a string of digits or a number; anything else is 400.
- Answer: `{ items, total, page, pageSize, totalCapped? }` (the `…Page` schemas). `totalCapped: true` means counting
  stopped at `total` (the UI shows "N+"). A page past the end answers empty `items` with the real `total`. No list
  answers an unbounded array.
- Bulk answers: `{ done: string[], skipped: { id, code }[] }` ([BulkResult](schemas/BulkResult.json)); a protected
  row is skipped with its error code, the rest are applied, and only `done` rows reach the activity log.

### Rules a JSON Schema can't carry

- [ActivityQuery](schemas/ActivityQuery.json), [AuthLogQuery](schemas/AuthLogQuery.json): `from` and `to` come as a
  pair of calendar dates in the app time zone (both days included), `to` ≥ `from`, at most 92 days apart.
  `format=csv` answers `text/csv` (attachment) with the whole filtered list, newest first, up to 10,000 rows; a cell
  that starts with `=`, `+`, `-`, `@`, tab or CR (after optional spaces) gets a leading `'`.
- [CreateUserBody](schemas/CreateUserBody.json): a directory (LDAP) user has neither `password` nor `invite`; any
  other user has exactly one of them.
- [UpdateRoleBody](schemas/UpdateRoleBody.json): `add` and `remove` apply to the role's current permissions and may
  not share a name. Nothing to change → 200 with the role, no activity entry.
- [CreatePermissionsBody](schemas/CreatePermissionsBody.json): the part before the dot is a module of the catalog
  (`packages/shared/src/permissions.ts`); the catalog holds at most 500 names (more is 400).
- No privilege escalation: a role's permissions can be added or removed, and a role can be given to or taken from a
  user, only by an actor who holds every permission involved (403 `forbidden`).
- A module's `view` comes with its other actions: a role that holds `user.create`, `user.edit` or `user.delete` also
  holds `user.view` (the same for `role.*` → `role.view`, `permission.create` → `permission.view`). `POST /api/roles`
  and `PATCH /api/roles/{id}` add it (and it counts for the escalation check); removing `view` while another action of
  the module stays leaves it on.
- Roles are referenced by name (users hold role names, like the source app). Names are unique ignoring letter case,
  and every lookup (`roles` in user bodies, the `role` filter, bulk `role`) ignores case and stores the role's own
  name. A rename (`PATCH /api/roles/{id}` with `name`, letter case included) moves every holder to the new name in the
  same step; a request that still sends the old name is 400 `bad_request` (unknown role).
- [PermissionDto](schemas/PermissionDto.json): `roles` lists at most 10 role names (A–Z), `roleCount` is how many
  roles hold the permission.
- `PATCH /api/users/{id}` checks every rule before changing anything. Changed fields (`name`, `username`, `email`,
  `roles`) write one `user.update` entry with only those fields; a status change writes `user.activate` /
  `user.deactivate`, the same rule and entry as `POST /api/users/{id}/status` and bulk activate / deactivate.
  Nothing to change → 200 with the user, no entry.
- Bulk `assignRole` skips a user who already holds 20 roles (the most one user holds) with `bad_request`.
- Actor rank: an actor may act on another user (`PATCH`/`DELETE /api/users/{id}`, `/status`, `/reset-password`,
  `DELETE /api/users/{id}/sessions/{sid}`, every bulk action) only when they hold every permission that user has
  (their effective permissions, the union of their roles). Otherwise 403 `forbidden`, checked after the 404 and before
  the other rules; bulk skips such a row with `forbidden`. So a `user.edit` holder can't reset, edit, deactivate,
  delete or sign out a Superadmin. The rows of `GET /api/users` and `GET /api/users/{id}` carry `permissions` so the
  screen can block those actions up front.
- Every POST/PATCH/PUT/DELETE outside `/api/auth/*` that changes something writes an activity entry; sign-in, sign-out
  and 2FA steps write sign-in log entries. `POST /api/me/reauth` is an auth step and writes neither.

### Activity log entries

Each entry: `{ id, at, actor: { id, name }, action, target: { type, id, label }, before, after }`
([ActivityDto](schemas/ActivityDto.json)). `before` / `after` are plain-data snapshots taken when the entry is written
(later edits don't change history) and are `null` when the action has none. Masking: a record's own credential fields
(`passwordHash`, `totpSecret`, `pendingTotpSecret`, `recoveryCodes`) are dropped, and any other field whose name
matches `password|secret|token|recovery` (any letter case, at any depth) keeps only `"••••"` when it had a value

### Backend notes

- Each area is a module of `apps/api/src/modules/` (controller, service, Drizzle schema, pure rules) that owns its
  tables; every query goes through Drizzle's builder, migrations are drizzle-kit output plus custom SQL in
  `apps/api/drizzle/`. The rules for adding to it are `AGENTS.md` §12 and §13.
- A change and its activity entry commit in one transaction. Rules two requests could both pass (the last active
  Superadmin, the 500-name catalog) are checked under a PostgreSQL advisory lock, and the actor's permissions and the
  target's rank are read inside the transaction after the row lock.
- Every connection runs with a 5 s statement timeout; lists count at most 100,000 rows (`totalCapped` beyond).
- Users list: `q` searches name, username and email with a substring match (`ILIKE`, served by trigram GIN indexes,
  `apps/api/drizzle/0001_custom.sql`). `GET /api/users/{id}` reads the last 20 entries targeting the user (index
  `activity (target_id, at DESC)`). `RoleDto.userCount` is a `GROUP BY role` count over the user–role table, not a
  per-role query.
- Recovery codes: 8 codes of 80 random bits each, stored as Argon2id hashes, spent on use.
- Google/Apple sign-in and linking: the state is stored hashed and is valid once for 10 minutes. It is bound to the
  browser by the `sk_oauth` cookie and to the browser's session when there is one: ending that session (sign-out,
  revoke) cancels the round trip, and a sign-in through the provider ends it. A link needs that session to be live at
  the callback. A second start in another tab replaces the first (one `sk_oauth` per browser). Starts: 20 per minute
  per client IP, 300 in all.
- Reset and invitation links: 32 random bytes (base64url), stored only as a SHA-256 hash, one live link per user
  (a new one replaces the old), single use (spent even when expired), valid 30 minutes (reset) or 72 hours
  (invitation). They are spent by a password change, an admin reset and deleting the user. A reset by link ends all
  of the user's sessions.

## Seed data

`bun run db:seed` (`apps/api/src/db/seed/system.ts`) writes the permission catalog, the roles Superadmin (every
permission, locked), Admin (all but `role.*` and `permission.*`) and Viewer (`user.view`, `audit.view`), and the
Superadmin named by `SEED_SUPERADMIN_*`. `bun run db:seed:demo` (`apps/api/src/db/seed/demo.ts`, refused in production)
adds the demo users, activity and sign-in log entries; the sign-in accounts are listed in the root README.
`bun run db:reset` drops the schema, migrates and runs both.
